## 我想解决的问题

直接向模型提问，回答可能看起来完整，却没有办法检查它依据的是哪份资料。我想做一个能看到检索过程的技术文档问答工具：先找原文，再组织回答；如果效果不好，能区分资料、切分、排序、上下文和生成各环节的问题。

这是个人学习与求职项目。目标是做出可以演示、可以复盘的完整链路，并通过小实验说明工程取舍。

## 为什么先做 BM25

BM25 的关键词匹配方式比较直观，不依赖模型 API，也方便查看某个问题命中了哪些词、哪几个片段。使用 jieba 进行中文分词后，我先用它建立基线，避免同时引入嵌入模型、向量索引和生成模型，让错误来源难以分清。

后来加入本地 BGE + FAISS 对照时，固定语料与判据，只改变检索排序方法。结果并不是“换成向量就更好”：Top-1 提升，Top-3 和 Top-5 下降。这支持先保留 BM25、继续看逐题差异的决定。

## 如何让出处和上下文更清楚

1. 文档保留 `source_id`、原文标题、章节与来源 URL，片段有稳定的标识。
2. 学习库按标题和段落切分，设置 400 字符上限；长段需要继续拆分。当前形成 471 个片段，不表示每个片段恰好有 400 字。
3. BM25 使用包含标题、章节和正文的 `search_text` 排序；用户可以直接检查原文片段。
4. 生成前按同一来源、同一章节补入相邻上下文，缓解只检索到局部段落的问题。
5. 原始检索命中与同节补充分别记录、分别展示。检索指标只评价原始 Top-K，避免把后加的内容算成检索成功。

引用解析用于把回答中的片段标识与上下文对照。它检查“引用指向哪里”，不能单独证明“这句话确实被原文支持”。后者仍需要语义检查或人工复核。

## 如何判断检索有没有进步

自建 30 道题，覆盖概念、比较与描述式问题。其中 27 道题标注标准证据，3 道题观察资料外问题。标准证据可以指定片段，也可以指定精确章节或章节前缀；评测程序按统一判据匹配。

使用 Hit@1 / 3 / 5 判断标准证据是否进入前 K 条，使用 MRR@5 判断第一条正确证据的排序。生成时补入的同节上下文不参与计算；资料外问题不混入 27 道计分题的分母。

这些题目由项目自身设计，规模小，也可能受开发过程影响，因此不把结果当作通用能力排名。每一轮都保存题目、语料身份、配置与逐题结果，使结论可以检查。完整结果见 [评测说明](EVALUATION.md)。

## 从实验脚本到本地工具

| 环节 | 可展示的工作 | 对使用者的意义 |
|---|---|---|
| 工作台 | React 前端与本机 Python API；早期另有 Streamlit 页面 | 把问题、命中片段、出处与回答放在同一处检查 |
| 用户资料库 | 导入 `.txt` / `.md` 或粘贴文字，独立存储与检索 | 可以试用自己的资料，避免与固定评测库混在一起 |
| 批量问题 | 每批 1–20 道，状态记录与取消处理 | 比逐个手动提问更方便比较；真实生成需明确确认 |
| 报告导出 | CSV / DOCX 基于已保存结果导出 | 导出时不重新调用模型，保留结果与命中证据 |
| Windows 交付 | 本地启停、打包与托盘相关脚本 | 降低本机演示的操作成本；源码仓库不等于已经附带可执行安装包 |

这部分展示的是工程完整性。固定学习库上的命中率不能直接用于证明导入任意用户资料后的质量，也不能证明所有界面和打包路径都没有问题。

## 我的工作与 AI 辅助的边界

我负责定义要解决的问题、选择项目范围、组织资料与评测要求、提出验收条件、看结果并决定下一步，以及把失败和改动整理成自己能解释的复盘。

CodeBuddy / Codex 辅助实现代码、执行部分检查和提供复审意见。因此更准确的项目描述是“AI 辅助开发，个人主导需求、评测、验收与复盘”。我需要能解释关键代码的输入输出与设计依据；没有逐行理解的部分不包装成已经熟练掌握。

BM25 算法、jieba、BGE 模型、FAISS、React 和 Streamlit 都是已有方法或工具。项目成果在于把它们组织成可检查的链路、建立评测与做出有证据的取舍，而不是发明算法或训练大模型。

## 目前最值得继续做的事

先独立复核已保存的生成回答：逐条检查关键结论是否有原文支持、引用是否贴合、重要信息是否遗漏、资料外问题是否合理处理。完成后再根据 BM25 与向量方法互有胜负的题目，做一个有固定判据的小规模融合检索实验。

这两个步骤分别补强“回答是否可信”和“检索是否值得升级”，比直接增加更多页面或框架更有助于解释项目价值。
